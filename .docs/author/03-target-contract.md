# 03 - Target Contract (Public + Shared + Author)

Last updated: 2026-02-17

This is the strict implementation contract for `frontend-v2`.

## 1) Canonical Route Contract

Public:
- `/`
- `/login`
- `/register`

Shared:
- `/role`
- `/notifications`
- `/profile/[user_id]`
- `/role/reviewer` (placeholder page only in this phase)
- `/role/chair` (placeholder page only in this phase)

Author:
- `/role/author`
- `/role/author/conferences/[conferenceId]`
- `/role/author/submissions`
- `/role/author/submissions/new`
- `/role/author/submissions/[submissionId]`
- `/role/author/submissions/[submissionId]/edit`

## 2) Route Parameter Naming

Use these exact names in route segments and helper builders:
- `conferenceId`
- `submissionId`
- `user_id`

Do not use legacy variants in canonical routes (`id`, `paperId`, `submission_id`, etc.).

## 3) Source-Of-Truth Decisions In This Phase

1. Notifications page source-of-truth:
- Keep feature behavior from `frontend/app/notifications/page.tsx`.
- Remove duplicate `/dashboard/notifications` feature route from final `frontend-v2` contract.

2. Author submission detail source-of-truth:
- Use API-backed flow from legacy `frontend/app/dashboard/conference/[id]/submission/[submissionId]/page.tsx` and `components/author/submission-detail/*`.
- Do not keep mock-based `/dashboard/author/papers/[id]` path as canonical.

3. Author dashboard source-of-truth:
- Use `components/author/author-conferences.tsx` route entry behavior.
- `components/author/author-dashboard.tsx` is legacy/unused and not part of canonical path contract.

4. Profile route source-of-truth:
- Use behavior from legacy `frontend/app/dashboard/users/[email]/page.tsx`, but remap to `/profile/[user_id]` with frontend resolver.

## 4) Auth And Session Contract

1. After successful login, route directly to `/role`.
2. `/role` must always force role re-selection for the session.
3. Role entry then routes to canonical role root:
- author -> `/role/author`
- reviewer -> `/role/reviewer` (placeholder in this phase)
- chair -> `/role/chair` (placeholder in this phase)
4. Placeholder pages must never try to render reviewer/chair business flows in this phase; they only show "not migrated yet" state and allow returning to `/role`.

## 5) Shared Navigation Contract

All shared nav components in `frontend-v2` must point to canonical routes for migrated scope.

### 5.1 Header

For author context:
- Dashboard -> `/role/author`
- My Submissions -> `/role/author/submissions`
- Notifications dropdown "See all" -> `/notifications`
- Profile menu -> `/profile/[user_id]` for current user
- Switch role -> `/role`

### 5.2 Sidebar (author context)

- Dashboard -> `/role/author`
- My Submissions -> `/role/author/submissions`
- Notifications -> `/notifications`

No author sidebar item should target `/dashboard/*`.

## 6) Behavior Contract For Author Flows

### 6.1 Conference navigation

Any author conference navigation target must be:
- `/role/author/conferences/[conferenceId]`

### 6.2 Submission list/detail/edit

1. Submission list row click:
- `/role/author/submissions/[submissionId]`

2. Submit new:
- `/role/author/submissions/new`
- still supports optional query prefill for `conferenceId` if needed

3. Edit existing:
- `/role/author/submissions/[submissionId]/edit`
- if conference context is required for API, include query: `?conferenceId=...`

4. Detail page:
- API-backed fetch remains conference-scoped on backend endpoint:
  - `/api/v1/conferences/{conferenceId}/submissions/{submissionId}`
- frontend route remains author-scoped and resolves `conferenceId` by this strict order:
  1) URL query param `?conferenceId=...`
  2) Resolve via `getUserSubmissions(user.email)` and match the `submissionId`
  3) If still unresolved, show not-found/invalid-link state with back link to `/role/author/submissions`
- Canonical deep links generated by UI should always include `conferenceId` to avoid extra lookup calls.

## 7) Data/API Contract (No Backend Change)

Allowed constraints:
- Keep existing backend endpoints.
- Continue using `/api/backend` proxy and current auth cookies.

Profile constraint:
- Backend user detail endpoint is email-keyed.
- Frontend must resolve `user_id -> email` before requesting non-self profile.

Profile resolver contract (strict order):
1. If `user_id === "me"`, fetch `/api/v1/users/me`.
2. If `user_id` equals current authenticated user id, fetch `/api/v1/users/me`.
3. If `user_id` looks like an email (`contains "@"`), treat as compatibility slug and fetch `/api/v1/users/{email}`.
4. Else call `/api/v1/users/search?q={user_id}&limit=10`, find exact id match from returned users, then fetch `/api/v1/users/{email}`.
5. If no mapping found, show not-found state (do not redirect loop, do not crash).

Fallback contract for unresolved user_id mapping:
- If resolver cannot map `user_id` to email, show a non-destructive not-found UI in `/profile/[user_id]` and provide back navigation.

## 8) Legacy Route Policy In `frontend-v2`

Final `frontend-v2` should not expose legacy author/shared/public paths:
- `/dashboard/*`
- `/author/conference/*`
- `/dashboard/notifications`
- `/dashboard/users/*`

Temporary compatibility wrappers are allowed during active implementation only and must be removed before phase completion.

## 9) Non-Goals For This Phase

- Reviewer route migration
- Chair route migration
- Admin migration
- Cross-role query-tab cleanup outside shared/public/author impact
